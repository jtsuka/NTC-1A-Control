# 外注負荷ヒートマップ / 日程リスク可視化 仕様書
## Ver0.5.9.1 ― kintone標準一覧「絞り込み」連動・再描画保険版
### Claudeクロスレビュー反映版 / 2026-09-08

- 対象：kintone App 272「外注課発注データ-TEST」
- ベース：Ver0.5.8 Manual可視化版
- 位置づけ：見た目・操作性に関する優先改善
- 今回の主目的：**kintone標準の絞り込み条件を、上段ヒートマップ／リスク一覧／下段ガントへそのまま反映する**

---

## 1. 改正理由

既存の無料ガントチャートプラグインでは、kintone標準の「絞り込み」を実行すると、
ガントチャートに表示される案件も同じ条件に絞られる。

現場では以下の使い方が想定される。

- 指示先名で絞り込む
- 手配担当者で絞り込む
- 手配書番号で絞り込む
- その他のkintone標準フィールド条件で絞り込む

一方、Ver0.5.8までの独自ヒートマップは、
カスタムビュー表示時にApp272から独自条件で全件を再取得していたため、
kintone画面上で絞り込みを行ってもヒートマップ側へ反映されなかった。

そのままでは利用者から
「標準ガントでは絞り込めるのに、この画面では絞り込めない」
と評価される可能性が高い。

そのためVer0.5.9では、
**新しい独自フィルターUIを作るのではなく、利用者が既に使い慣れているkintone標準絞り込みをそのまま利用する**
方針とする。

---


## 2.1 Claudeクロスレビュー反映：再描画ガード修正

Ver0.5.9初版では、既存の二重描画防止として以下のガードが残っていた。

```javascript
if (root.dataset.initialized === '1') return event;
```

このままでは、kintoneが絞り込み変更時にカスタムビューのDOMを使い回した場合、
`index.show` が再発火しても `fetchActiveRecords()` が呼ばれず、
前回条件のヒートマップが残る可能性がある。

Ver0.5.9.1では、現在の標準一覧絞り込み条件を先に取得し、

- 前回条件と同一 → 重複描画としてスキップ
- 前回条件と異なる → 強制的に再取得・再描画

とする。

概念：

```javascript
const current = kintone.app.getQueryCondition();
const previous = root.dataset.listQueryCondition;

if (initialized && previous === current) {
  return;
}

// 条件が変わっていれば再取得
```

さらにAPI取得失敗時は `initialized` を解除し、
同一条件でも再試行可能とする。

これにより、
**二重描画抑止と、絞り込み変更時の確実な再取得を両立する。**

## 2. 操作仕様

利用者は従来どおり、kintone一覧画面の漏斗アイコンから絞り込み条件を指定する。

例：

```text
指示先名 = ㈱山和（八尾）
```

または、

```text
手配担当者 = 宮田
```

絞り込み適用後にカスタムビューが表示されると、
ヒートマップJSは現在の一覧に設定されている絞り込み条件を取得し、
その条件に一致するレコードだけを取得・集計する。

対象となる表示：

1. 上段サマリー
2. 外注先 日次同時案件数ヒートマップ
3. 要注意／リスク一覧
4. 下段の外注先別案件詳細ガント

すべて同じ `state.records` を利用しているため、
取得対象を絞ることで画面全体が同じ条件へ連動する。

---

## 3. kintone標準JavaScript APIの利用

現在開いている一覧の絞り込み条件取得には、

```javascript
kintone.app.getQueryCondition()
```

を使用する。

このAPIは一覧の絞り込み条件のみを返し、
`order by`、`limit`、`offset` は含まない。

このため、

- kintone画面が「20件表示」でも20件だけには限定しない
- 標準一覧の並び順には依存しない
- 絞り込み条件に一致する対象レコードを500件ずつ全件取得できる

構成とする。

`kintone.app.getQuery()` は表示件数やoffset等も含むため、
今回の用途では使用しない。

---

## 4. Ver0.5.8までの固定対象条件

既存ヒートマップでは、

```text
納期 >= 今日
```

を対象条件としている。

Ver0.5.9でもこの条件は変更しない。

したがって実際のAPI条件は概念的に、

```text
(kintone標準一覧の絞り込み条件)
AND 納期 >= 今日
AND $id > 前回取得したID
ORDER BY $id ASC
LIMIT 500
```

となる。

### 重要

kintone標準一覧の絞り込み結果に「過去納期の案件」が含まれる場合、
kintone画面上の件数とヒートマップの「対象件数」は一致しない場合がある。

これは絞り込み連動の不具合ではなく、
Ver0.5.8以前から存在する「納期が今日以降のみをヒートマップ対象とする」固定仕様による。

今回の改修では、この既存対象条件を勝手に変更しない。

---

## 5. 取得処理

### 5.1 絞り込み条件取得

カスタムビュー表示イベント：

```javascript
app.record.index.show
```

内でレコード取得を開始する際、

```javascript
const listCondition =
  String(kintone.app.getQueryCondition() || '').trim();
```

として現在の絞り込み条件を取得する。

---

### 5.2 500件ページング

既存方式を維持し、

```text
$id > lastId
order by $id asc
limit 500
```

で繰り返し取得する。

一覧画面のページサイズが20件、50件、100件等であっても、
ヒートマップは表示中ページだけでなく条件一致レコード全体を取得する。

---

## 6. 画面表示

既存の見た目は原則変更しない。

対象件数表示の横に状態を追加する。

絞り込みがある場合：

```text
対象 49件 / 外注先 1社　一覧絞込：適用中
```

絞り込みがない場合：

```text
対象 160件 / 外注先 27社　一覧絞込：なし
```

目的は、
「今このヒートマップがkintoneの絞り込み条件に従っている」
ことを利用者が画面上で確認できるようにすることである。

---

## 7. 絞り込み対象フィールド

特定フィールド専用の実装にはしない。

kintone標準一覧で指定可能な条件であり、
REST APIのレコード取得クエリとして利用可能であれば、
現在の一覧条件をそのまま利用する。

想定例：

- 指示先名
- 手配担当者
- 手配書番号
- 納期
- 商品名
- その他App272フィールド

これにより、将来項目が増えても
ヒートマップJS側へ個別の検索UIを追加する必要を減らす。

---

## 8. 既存機能への影響

以下は変更しない。

- 30 / 60 / 90日表示
- 標準 / 大 / 特大表示
- 外注先の日別同時案件数計算
- 0件＝白、1～2件＝緑、3～4件＝黄、5件以上＝赤
- 最大同時案件
- 日付矛盾判定
- 要注意判定
- 手配日 / 加工着手日 / 完成検査日 / 納期マーカー
- Manual案件のMバッジ
- Manual案件の太枠
- Manual案件の淡い背景
- 赤＝日付矛盾・要注意
- レコードリンク
- 日付編集はkintone標準レコード画面で行う
- K日程フィールドの自動更新は行わない

今回の変更は、
**取得するレコード集合をkintone標準絞り込みへ連動させることが中心**
であり、集計・描画ロジック自体は変更しない。

---

## 9. 性能面

絞り込み条件によって取得レコード数が減る場合、
従来よりAPI取得件数・描画件数とも減少するため、
画面表示が軽くなる可能性がある。

一方、絞り込みなしの場合はVer0.5.8と同じ取得方式・同程度の負荷となる。

新たに大量のDOM要素を追加する改修ではないため、
本変更単体による描画負荷増加は小さい。

---

## 10. エラー処理

標準一覧の絞り込み条件をREST APIへ適用した結果、
APIエラーが発生した場合は既存仕様どおり、

- コンソールへエラー出力
- カスタムビュー内に「データ取得に失敗しました」を表示

する。

絞り込み条件を黙って無視して全件表示へ戻す処理は行わない。

理由：
利用者が「絞り込まれている」と誤認して全件データを見ることを防ぐため。

## 12. Claudeクロスレビューで確認してほしい点

1. `kintone.app.getQueryCondition()` の利用方法は適切か
2. 取得した条件を括弧で囲み、固定条件と `and` 結合する方法に問題がないか
3. `$id > lastId` による500件ページングと任意の一覧絞り込み条件を組み合わせても取りこぼしがないか
4. 一覧画面のlimit / offsetを引き継がない方針は妥当か
5. 絞り込み条件にユーザー選択・組織選択等が含まれる場合のkintone固有注意点はないか
6. 絞り込み条件と `納期 >= 今日` の固定条件の関係が仕様として明確か
7. 絞り込み適用中で0件となった場合の描画に問題がないか
8. Ver0.5.9.1の「前回条件と現在条件の比較」により、DOM再利用時にも古い条件が残らないか
9. 絞り込み変更時の `app.record.index.show` 再発火と、条件差分による再取得が実機で期待どおり動くか
10. 現行Ver0.5.8のManual可視化・集計・ガント表示への副作用がないか
