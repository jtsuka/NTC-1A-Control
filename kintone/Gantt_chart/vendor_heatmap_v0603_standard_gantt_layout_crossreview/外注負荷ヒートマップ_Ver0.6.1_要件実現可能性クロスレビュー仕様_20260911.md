# 外注負荷ヒートマップ Ver0.6.1 要件・実現可能性クロスレビュー仕様

作成日: 2026-09-11
対象: kintone App 272 / 外注課発注データ-TEST
基準実装: `vendor_heatmap_v0603_standard_gantt_layout.js` (Ver0.6.0.3)
状態: **SPEC REVIEW ONLY / 実装禁止**

---

## 1. 目的

Ver0.6.0.3 の既存機能・レイアウトを壊さず、kintone標準一覧の絞り込み結果を尊重したまま、ユーザーが今日より前の日程を横スクロールで確認できるようにする。

今回の最重要方針は、**既存完成版 Ver0.6.0.3 を母体とし、変更範囲を最小化すること**である。Ver0.6.1 を別物として再実装しない。

---

## 2. 変更しないもの（絶対維持）

Ver0.6.0.3 の以下をそのまま維持する。

- 上段: 外注先別 日次同時案件数ヒートマップ
- サマリー表示
- 日付矛盾 / 要注意表示
- Manual表示（M）
- 表示サイズ切替
- 外注先行クリックによる下段切替
- 下段ガントの列構成・レイアウト
- 日程ひげチャート

  - 仕掛開始 → 検収日: 太線
  - 検収日 → 納期: 細線（右ヒゲ）
  - ○ / ▶ / ● / ◆ の各マーカー
- 既存の危険判定・色分け
- レコードリンク
- 閲覧専用であること
- K日程種別や日程フィールド等への書込みを一切行わないこと

### 禁止事項

- 新規の独自検索UI追加
- kintone標準絞り込みと別の業務条件をJS内部に隠して追加

## 3. 新規要求

### R1. kintone標準絞り込みを業務母集団の唯一の条件とする

`kintone.app.getQueryCondition()` で取得した標準一覧の絞り込み条件をそのまま使用する。

JS内部に固定していた以下の条件は廃止する。

- `納期 >= 今日`

JSが追加してよいのは技術的なページング条件のみ。

例:

- `$id > lastId`
- `order by $id asc`
- `limit 500`

### R2. 過去最大90日を横軸内部に保持する

表示横軸は次の範囲を持つ。

- 左端: 今日 - 90日
- 基準: 今日
- 右端: 今日 + 表示期間 - 1日
- 表示期間: 既存の30 / 60 / 90日を維持

過去側90日は固定上限とし、案件1件の古い日付だけで90日より前へ自動拡張しない。

### R3. 初期表示は必ず「今日」付近

内部横軸が今日-90日から始まっていても、画面初期表示時は今日列が左側付近に見える位置へ自動スクロールする。

ユーザーが最初に6月など90日前の先頭を見せられる状態はFAIL。

### R4. 左スクロールで過去を閲覧できる

初期表示後、ユーザーが標準の横スクロールバーで左へ移動すると最大90日前まで確認できる。

### R5. 「今日へ戻る」操作

過去側へ移動後、ワンクリックで今日位置へ戻れる操作を追加してよい。

既存UIを圧迫しない小さなボタンとする。

### R6. 髭チャートは過去範囲でも正しくクリップ表示する

案件日程が表示範囲外に一部はみ出す場合でも、既存の意味を壊さない。

例:

- 手配日が90日より前、仕掛開始が範囲内 → 左ヒゲは左端でクリップ
- 納期が未来表示期間より後 → 右ヒゲは右端でクリップ
- 4日付すべて範囲内 → 従来どおり完全表示

### R7. 上段と下段の時系列認識を矛盾させない

上段ヒートマップと下段ガントは同一の表示開始日・終了日を使う。

スクロール同期は望ましいが、実装難度・既存DOM構造への影響が大きい場合はVer0.6.1必須要件としない。

**優先順位:**
1. 既存表示を壊さない
2. 初期今日位置
3. 左へ過去90日閲覧
4. 上下スクロール同期

## 4. 実現可能性の事前評価

### F1. 標準絞り込み優先

**実現可能: 高**

既存の `fetchActiveRecords()` で、固定 `納期 >= 今日` 条件を除去し、標準一覧条件 + ページング条件だけにすることで対応可能。

### F2. 過去90日の横軸保持

**実現可能: 高**

既存 `render()` で現在 `today ～ end` としている期間を `today-90 ～ end` に変更することで対応可能。

ただし、この変更により既存ガントの1日マス数が増えるため、CSS幅・sticky列・スクロール領域の既存挙動を実機確認する必要がある。

### F3. 初期位置を今日にする

**実現可能: 中～高**

既存の `.eh-schedule-scroll` 等の実際の横スクロールコンテナを特定し、DOM描画後に `scrollLeft` を設定することで実現可能。

注意点:
- kintone描画タイミング
- sticky固定列分のオフセット
- ブラウザ差
- 上段と下段でスクロールコンテナが別の場合

このため、実装前に「どのDOMがscrollLeftを持つか」をVer0.6.0.3で確認すること。

### F4. 髭チャート維持

**実現可能: 高**

既存 `renderVendorDetail()` / `renderTrackBands()` / `cellSpanStyle()` 等を変更せず、viewStart/viewEndのみ拡張する方針なら回帰リスクを最小化できる。

### F5. 上下スクロール同期

**実現可能: 中**

実装自体は可能だが、既存の上段・下段DOM構造とsticky列を確認してから判断する。

Ver0.6.1の必須要件にはしない。同期が既存表示を壊す懸念があれば後続版へ送る。

## 5. 実装方針（クロスレビュー承認後のみ）

### 原則

**Ver0.6.0.3の完全コピーを新ファイル化し、差分だけ入れる。**

変更候補は以下に限定する。

1. `CONFIG` に `pastDays: 90` を追加
2. `fetchActiveRecords()` からJS固定の `納期 >= 今日` を削除
3. `render()` の `viewStart` を `today - 90日` に変更
4. 既存の `viewEnd` は30/60/90日選択を維持
5. 初期描画後に既存横スクロールコンテナを今日位置へ移動
6. 必要なら「今日へ戻る」ボタンを既存headerに最小追加

### 原則として触らない関数

- `renderVendorDetail()`
- `renderTrackBands()`
- `renderScheduleDateHeader()`
- `cellSpanStyle()`
- `evaluateRisk()` 等の危険判定関数
- 既存のガント行HTML生成
- Manual表示ロジック

## 7. PASS / FAIL基準

### PASS

- Ver0.6.0.3の既存機能をすべて維持
- 初期表示が今日
- 左へ最大90日戻れる
- 髭チャートが正常
- kintone標準絞り込みが母集団の唯一の業務条件
- 30/60/90日切替正常
- 書込みなし

### FAIL

以下のいずれかで即FAIL。

- 初期表示が90日前から始まる
- 髭チャートが1件でも構造的に消える
- 下段の列/レイアウトが崩れる
- サマリー・Manual・リスク表示が消える
- JSが標準絞り込み以外の固定業務条件を追加する
- レコードを書き換える
- Ver0.6.0.3より主要機能が減る

## 8. クロスレビュー依頼事項

Claude / ChatGPT 双方で、実装前に以下をレビューする。

1. 要求に矛盾がないか
2. Ver0.6.0.3のDOM/CSS構造で横スクロール方式が実現可能か
3. 初期scrollLeft設定の最も安全なDOM対象はどこか
4. sticky列との相互作用
5. viewStartを90日前へ動かすことで既存 `cellSpanStyle()` 等が破綻しないか
6. 標準一覧条件 + `$id` ページングのクエリ生成に問題がないか
7. 上下スクロール同期をVer0.6.1に含めるべきか、後続に分離すべきか
8. 追加で必要な回帰試験がないか
9. 「最小差分」の範囲を逸脱していないか

レビュー結果は以下で判定する。

- **GO**: 実装へ進む
- **GO WITH CONDITIONS**: 条件を仕様へ追記してから実装
- **NO-GO**: 方式再検討

## 9. 今回の教訓

先行Ver0.6.1で、既存完成版を簡略化して再実装した結果、髭チャート・初期位置・レイアウト等に回帰が発生した。

今後は以下を厳守する。

- 既存FORMAL PASS版を母体とする
- 差分を限定する
- 要求→実現可能性→クロスレビュー→実装→実機試験の順序を守る
- 実装前にロールバック点を確保する
- 1つの改修で複数の既存機能を作り直さない
