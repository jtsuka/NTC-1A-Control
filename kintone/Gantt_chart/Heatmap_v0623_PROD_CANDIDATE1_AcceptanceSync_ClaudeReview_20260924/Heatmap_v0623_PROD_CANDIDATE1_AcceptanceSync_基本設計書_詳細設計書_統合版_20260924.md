# 0. 文書の目的

本書は、App272「外注課発注データ」に実装した独自の外注負荷ヒートマップ／案件詳細ガントと、App293の受入実績からApp272の「受入れ日」を安全に反映するAcceptanceSync機能について、2026-09-24時点で確定した仕様を一本化したものである。

初期のプレビュー仕様、旧TISガント、旧Lookup互換処理、固定3日／5日の日程案など、開発途中の仕様はそのまま最終仕様とはしない。本書では、後続の実機確認、PowerShell自動取込、NoJOIN／NoLookup化、Claudeクロスレビューによって確定した内容を優先する。

本システムの基本思想は次のとおりである。

1.  **基幹データと現場管理データを分離する。**
2.  **発注番号をApp272の業務上の一意キーとして扱う。**
3.  **日程は外注先別マスタを用いて算出し、手動変更を最優先で保護する。**
4.  **ヒートマップは「自動最適化」ではなく、負荷の山を見える化して現場判断を支援する。**
5.  **受入実績同期は、単一受入など安全に意味を確定できる案件だけを書込み候補とする。**
6.  **複数受入を機械的に完納扱いしない。**
7.  **書込み前に再分析し、revision・候補値・分類が変化した場合はFail
    Closedとする。**
8.  **書込み対象フィールドを必要最小限に限定する。**

# 第I部 基本設計

# 1. システム概要

## 1.1 業務目的

外注課の発注案件について、外注先別の負荷状況と各案件の日程を同一画面で確認できるようにし、次の業務を支援する。

-   外注先ごとの日別案件集中状況の把握
-   加工着手日から完成検査日までの予定確認
-   手配日、加工着手日、完成検査日、納期の時系列確認
-   納期変更や日程矛盾の発見
-   手動調整済み日程の識別
-   外注入荷実績の登録・修正・取消
-   PRONES由来の受入実績とApp272「受入れ日」の照合・安全な反映
-   将来の外注先との日程調整、山ならし検討のための実績蓄積

本機能は、外注先能力を自動的に断定したり、最適日程を自動決定したりするものではない。現場が外注先と調整するための**可視化・提案・コミュニケーション支援**を目的とする。

# 4. キー設計

## 4.1 App272主キー

App272では**発注番号**を業務上の一意キーとする。

発注番号と、手配書番号／注文書番号は別概念である。

-   発注番号：App272の案件識別キー
-   手配書番号：営業注文等から派生した上位の関連番号
-   注文書番号：別の業務識別番号

AcceptanceSyncでも発注番号をApp293とApp272の突合キーとして使用する。

## 4.2 重複禁止

App272に同一発注番号が複数存在すると、どのレコードへ受入日を書き込むべきか一意に決められない。

したがってAcceptanceSyncでは、

> **App272同一発注番号重複 = SafetyStop**

とする。

1件でも重複を検出した場合、対象レコードだけを除外して続行するのではなく、分析／Execute全体を停止する。

# 5. 日程管理基本設計

## 5.1 日程種別の優先順位

最終仕様では日程由来を以下で管理する。

**Manual \> Batch \> Auto**

  種別     意味
  -------- ------------------------------------------
  Manual   人が意図的に調整した日程
  Batch    PowerShell／朝バッチで計算・設定した日程
  Auto     ブラウザJS等による自動計算日程

Manualを最優先で保護する。

既存Manual／Batchは原則として自動処理から保護する。既存Autoまたは空欄は、条件によりBatch再計算候補とする。

## 5.2 外注先別日程マスタ

固定「納期3日前／完成検査日5日前」の初期プレビュー案は最終ロジックではない。

正式系では外注先別日程マスタ

`C:\HPDB\加工先別_日程暫定シート_20260910.xlsx`

を参照する。

会社カレンダー:

`C:\HPDB\カレンダー(2023).xlsx`

祝日:

`C:\HPDB\JapanHolidays_2026_2027.csv`

計算は、マスタで定義した暦日差引を行った後、

-   完成検査日：必要に応じて**前営業日**
-   加工着手日：必要に応じて**翌営業日**

へ補正する。

## 5.3 手動日程保護

Manual日程は基幹納期変更やマスタ変更があっても自動上書きしない。

矛盾が発生した場合は日程を勝手に修正するのではなく、画面上の警告によって人へ判断を返す。

# 6. ヒートマップ基本設計

## 6.1 上段ヒートマップ

外注先ごとに日別の同時案件数を集計し、負荷の山を視覚化する。

目的は「能力値を断定する」ことではなく、

-   どの日に案件が集中しているか
-   どの外注先に山があるか
-   日程調整の相談候補がどこか

を把握することである。

## 6.2 下段案件詳細ガント

各案件について、日付軸上で予定を表示する。

主要な時系列:

``` text
手配日
  ↓
加工着手日
  ↓
完成検査日
  ↓
納期
```

日程矛盾やリスクがある場合は警告表示する。

## 6.3 標準一覧フィルタ連動

独自ヒートマップは、kintone標準一覧の絞り込み条件を尊重する。

`kintone.app.getQueryCondition()` で標準一覧条件を取得し、同じ対象集合を

-   上段ヒートマップ
-   リスク表示
-   下段ガント

へ適用する。

独自画面だけ別条件で全件を表示してはならない。

## 6.4 固定列

標準ガント風の固定列として、主要識別情報を左側に保持する。

確定した基本構成:

-   手配書番号／案件識別情報
-   指示先名（外注先）
-   手配担当者

横方向に日付軸をスクロールしても案件識別情報を追跡できる構成とする。

## 6.5 期間表示

ヒートマップ／ガントは期間切替を持ち、30／60／90日等の表示期間を扱う。

表示期間変更や再描画後も、ユーザーが確認していた位置を不用意に失わないようスクロール位置を管理する。

## 6.6 今日付近への初期表示

初期表示では今日付近が見える位置へスクロールする。

ただし標準一覧で過去案件を明示的に絞り込んだ場合、それを独自側で勝手に除外しない。

## 6.7 Manual識別

手動調整日程は自動日程と視覚的に区別する。

既存仕様ではManual案件に対し、

-   `M` 表示
-   背景表現
-   太枠等

を用いて識別する。

目的は「人が決めた日程を自動計算値と誤認しない」ことである。

# 7. 外注入荷実績機能

## 7.1 外注入荷実績日

`外注入荷実績日`
は、外注先から実際に品物が到着した日をApp272内で記録するためのDATEフィールドである。

これはAcceptanceSyncの `受入れ日` とは独立する。

## 7.2 登録・修正

ガント画面内から入荷日を登録／修正できる。

ポップアップはクリックした行のボタン位置を基準に`getBoundingClientRect()`で座標を取得し、`document.body`直下へ`position:fixed`で表示する。

主なUI条件:

-   幅約220px
-   ラベルは折返しを避ける
-   画面右端／下端からのはみ出し補正
-   同時に開くポップアップは1つ
-   外側クリック、保存、キャンセルで閉じる
-   PUT中は不用意に閉じない

## 7.3 入荷取消

誤登録時は入荷済み案件の編集ポップアップから取消できる。

取消時に更新するのは、

`外注入荷実績日 = 空文字`

のみ。

K日程系フィールドへは触れない。

## 7.4 完了表示

入荷済み案件は下段ガントで完了状態としてグレー表示する。

ただし、外注入荷実績日が入っただけで上段ヒートマップの負荷集計から自動除外する仕様ではない。負荷表示と実績完了表示は別責務として扱う。

# 8. Windows横スクロール基本設計

Windowsの一般的な縦ホイールマウスでも扱いやすくするため、Shift＋縦ホイールを横スクロールへ変換する。

仕様:

-   通常ホイール：ブラウザ標準動作を維持
-   Shift＋`deltaY`主成分：横スクロールへ変換
-   `deltaX`主成分：ネイティブ横入力としてブラウザへ任せる
-   `deltaMode` 0/1/2を正規化
-   左右端でも自前変換時は`preventDefault()`
-   上段／下段スクロール領域は独立
-   再描画後に現在のDOMへイベントを再バインド
-   REST APIや日程データには一切影響しない

# 9. AcceptanceSync基本設計

## 9.1 目的

App293に蓄積されたPRONES受入実績を、発注番号でApp272へ突合し、安全に意味を確定できる案件だけApp272「受入れ日」へ反映する。

## 9.2 なぜ単純な「最新受入日コピー」にしないか

同一発注番号に複数の受入実績行が存在する場合、

-   分納
-   返品／マイナス数量
-   訂正
-   複数日にわたる受入

などが考えられる。

そのため、

> **MAX(受入日) = 完納日**

とは定義しない。

初版の自動反映対象は**単一受入でレビュー要因がない案件**に限定する。

複数受入は分析結果として提示するが、自動書込みしない。

## 9.3 AnalysisとExecuteの分離

AcceptanceSyncは二段階で動作する。

``` text
Analyze
  ↓
分類結果表示
  ↓
人が候補を選択
  ↓
Execute直前に再Analysis
  ↓
安全条件再確認
  ↓
PUT
  ↓
PostVerify
```

Analyzeだけでは書込みを行わない。

# 第II部 詳細設計

# 10. AcceptanceSync参照データ

## 10.1 Source App293

App293はAcceptanceSyncでは原則READ ONLY。

発注番号単位に受入実績をグルーピングする。

グループごとに以下を算出する。

-   `SourceRowCount`
-   `DistinctReceiptDateCount`
-   `FirstReceiptDate`
-   `LastReceiptDate`
-   `CandidateReceiptDate`
-   `NegativeReceiptCount`

候補日は分析上`LastReceiptDate`を保持するが、複数受入の場合に自動採用することを意味しない。

## 10.2 Target App272

App272から最低限以下を取得する。

-   発注番号
-   `$id`
-   `$revision`
-   現在の`受入れ日`

分析時点のID・revision・現在値をスナップショットとして保持し、Execute直前の再分析結果と比較する。

# 11. AcceptanceSync分類ロジック

最終Golden DryRunで扱う主要Classは以下である。

  --------------------------------------------------------------------------------------------------------------
  Class                      意味                                                                       自動候補
  -------------------------- ------------------------------------------------------ ----------------------------
  `CANDIDATE_EMPTY_SINGLE`   App272受入れ日空欄、App293単一受入、レビュー要因なし                            YES

  `CANDIDATE_EMPTY_MULTI`    App272受入れ日空欄、App293複数受入                                               NO

  `ALREADY_SAME`             App272受入れ日と候補日が一致                                               NO WRITE

  `EXISTING_DIFFERENT`       App272に既存日があり候補と異なる                                                 NO

  `SOURCE_REVIEW_REQUIRED`   App293側に異常／レビュー要因                                                     NO

  `SOURCE_ONLY_NO_APP272`    App293に実績あり、App272に同一発注番号なし                                       NO

  `NO_SOURCE_DATA_UNKNOWN`   App272にあるがApp293に確認できる受入実績なし                                     NO
  --------------------------------------------------------------------------------------------------------------

## 11.1 CANDIDATE_EMPTY_SINGLE

条件:

-   App272に対象発注番号が1件だけ存在
-   App272「受入れ日」が空欄
-   App293側の対象発注番号が単一受入
-   受入日が妥当な日付
-   マイナス受入等のレビュー要因なし

このときのみ`FutureAutoEligible=YES`。

## 11.2 CANDIDATE_EMPTY_MULTI

App293側に同一発注番号の複数受入がある場合。

候補として最終日を算出しても、自動書込み対象にはしない。

Reason:

> 受入れ日空欄 / 複数受入。MAX(受入日)は完納日と定義しない

## 11.3 NO_SOURCE_DATA_UNKNOWN

App293の直近取得範囲に受入実績が見つからないことは、

> 「未受入」

を意味しない。

取得期間外ですでに受入済みの可能性があるため、

> PRONES受入実績として確認できない（未受入とは判定しない）

として扱う。

# 12. Source安全チェック

分析開始時に少なくとも以下を検証する。

## 12.1 App293受入番号

-   空の受入番号がないこと
-   受入番号が重複していないこと

異常時はSafetyStop。

## 12.2 App272発注番号

同一発注番号が複数レコードに存在した場合はSafetyStop。

これはClaudeレビューで追加された重要条件であり、曖昧な書込み先を許容しない。

## 12.3 フィールドPreflight

必要フィールドが存在し、期待する型であることを確認する。

特に`受入れ日`はDATEフィールドであることを必須とし、不存在または型不一致時はFail
Closedとする。

# 13. Execute安全設計

## 13.1 PROD書込み対象

最終PROD候補では、

-   **App272のみExecute可能**
-   App293はREAD ONLY
-   App292はAnalysis Only

とする。

TEST段階ではApp292を用いてExecute経路を実証したが、最終PROD候補では誤書込み防止のため役割を反転させ、App272だけを本番書込み対象として固定する。

## 13.2 選択方式

一括自動全件更新ではなく、Analyze結果から人が候補を確認して選択する。

PROD候補の上限:

`MaxWrites = 50`

1回のExecuteで50件を超える書込みを許可しない。

## 13.3 Execute確認文字列

Executeには件数を含む確認文字列を要求する。

``` text
APP272-ACCEPTANCE-EXECUTE:<件数>
```

例:

``` text
APP272-ACCEPTANCE-EXECUTE:50
```

表示件数と確認文字列の件数が一致しなければ書込みしない。

## 13.4 Execute直前再Analysis

Analyze後に時間が経過するとApp272／App293が変更される可能性がある。

そのためExecuteボタン押下時には再度データを取得・分類し、選択時スナップショットと比較する。

以下のいずれかが変化した場合は**WRITE 0**で停止する。

-   App272 `$revision`
-   App272現在の`受入れ日`
-   CandidateReceiptDate
-   Class
-   対象発注番号の一意性
-   その他候補成立条件

## 13.5 書込みフィールド

AcceptanceSyncがPUTするフィールドは**`受入れ日`のみ**。

概念上のpayload:

``` json
{
  "id": "<App272 record id>",
  "revision": "<analysis時点と一致確認したrevision>",
  "record": {
    "受入れ日": {
      "value": "YYYY-MM-DD"
    }
  }
}
```

以下へは触れない。

-   `K加工着手日`
-   `K完成検査日`
-   `K日程種別`
-   `K計算根拠`
-   `K暫定設定`
-   `外注入荷実績日`
-   外注先
-   担当者
-   納期
-   その他基幹項目

# 14. PostVerify

PUT成功応答だけで完了扱いにしない。

書込み後、対象App272レコードを再GETし、全件について以下を検証する。

-   対象件数
-   対象発注番号
-   `受入れ日 == CandidateReceiptDate`
-   revision更新が成立していること
-   非対象レコードへ不要な変更がないこと

PostVerify不一致時は成功扱いにしない。

自動再試行で上書きを重ねる仕様にはしない。

# 17. ヒートマップ描画詳細

## 17.1 再描画

画面条件変更時は対象レコードを再取得／再分類し、上段・下段を再描画する。

再描画時には古い非同期処理が新しい画面へ混入しないよう、世代番号等のガードを用いる。

## 17.2 スクロール保持

次の操作後も必要に応じてスクロール位置を保持する。

-   外注先／標準フィルタ変更
-   再描画
-   入荷日登録・修正・取消

入荷日更新時は可能な限り全体`render()`を避け、該当行だけを更新する。

## 17.3 レコードリンク

案件詳細からkintone標準レコードへ移動できる導線を維持する。

独自画面だけで全編集機能を再実装するのではなく、必要に応じて標準フォームへ戻れる設計とする。

# 18. 外注入荷実績PUT詳細

## 18.1 更新対象

登録／修正／取消で更新するのは`外注入荷実績日`のみ。

## 18.2 revision guard

PUTには`$revision`を含める。

他ユーザーが同じレコードを更新した場合、古い画面状態で上書きしない。

## 18.3 二重送信防止

-   保存／取消ボタンdisable
-   `activeReceipt.saving`等の状態ガード
-   PUT中の外側クリック抑止

により二重PUTを防止する。

# 20. エラー／Fail Closed設計

以下は処理継続ではなく停止を基本とする。

-   必須フィールド不存在
-   `受入れ日`型不一致
-   App272発注番号重複
-   App293受入番号の不正
-   対象件数がMaxWrites超過
-   Execute確認文字列不一致
-   Execute直前のrevision変化
-   CandidateReceiptDate変化
-   Class変化
-   現在の受入れ日変化
-   PostVerify不一致

「危険なレコードだけ飛ばして残りを書く」より、書込み集合の意味が変わった時点で全体を止め、人に返す設計を優先する。

# 34. 最終設計原則

# 付録C. 用語

**AcceptanceSync**\
App293の受入実績を分析し、App272の独立DATEフィールド「受入れ日」へ安全に反映する機能。

**外注入荷実績日**\
外注先から現物が到着したことをApp272画面で記録する実績日。AcceptanceSyncの「受入れ日」とは別。

**Manual / Batch / Auto**\
K日程の由来。優先順位はManual \> Batch \> Auto。

**SafetyStop / Fail Closed**\
安全条件を満たさない場合に、一部だけ強行せず書込みを停止する考え方。

**PostVerify**\
PUT/POST後に対象を再GETし、意図した状態になったことを確認する工程。
