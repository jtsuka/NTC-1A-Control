# App272 受入更新「成果＋残課題」エビデンス出力仕様書
**版:** v0.3.1 FINAL / GO TO IMPLEMENTATION  
**日付:** 2026-10-04

## 1. 目的
AcceptanceSync完了後、App293の直近3か月受入データとApp272全対象を再分析し、
(1) 全件Analysis CSV＝成果＋全体状態、(2) 未受入期限超過CSV＝残課題、
(3) Summary、(4) RunId単位の追記専用状態遷移ログを正式証跡として残す。

## 2. 正本と責務
- kintone PUT＋PostVerifyが更新結果の正本。
- 証跡書込みは更新結果を左右しない。
- PUT/PostVerify成功後に証跡書込みだけ失敗した場合:
  `PUT_SUCCESS_EVIDENCE_WRITE_FAILED`
- この場合、PUTを失敗扱いに戻さず、自動再PUTもしない。
- ただし当該RunのEvidence ExportはFAIL/非0終了とし、証跡欠落を明示する。
- Export処理はApp272/App293に対してREAD ONLY。

## 3. 状態遷移ログの目的
状態遷移ログの目的は**再PUT防止ではない**。
既存AcceptanceSyncは毎回App272の現在値を再取得・再分類するため、
受入れ日が既に設定された案件は再び空欄候補として扱われない。

状態遷移ログの目的は次の2点。
1. クラッシュ・証跡生成失敗時に、どこまで処理が進んだかを事後診断できること。
2. 最終成果CSV/Summary生成が途中停止しても、完結したイベントから当日の更新事実を再構成できること。

## 4. 状態遷移ログ形式
JSON Lines（UTF-8、1行1JSON、追記専用）を採用する。
原則、既存行を上書き・編集しない。

ファイル例:
`App272_AcceptanceRun_YYYYMMDD_<RunId>.jsonl`

各イベント最低項目:
- SchemaVersion
- RunId
- EventType
- TimestampJST
- 発注番号
- App272RecordId
- RevisionBefore
- BeforeAcceptanceDate
- CandidateAcceptanceDate
- RevisionAfter
- AfterAcceptanceDate
- PostVerifyStatus
- ErrorCode / ErrorMessage（該当時）

EventType:
- `PRE_EXECUTE`
- `PUT_SUCCEEDED`
- `POST_VERIFY_PASS`
- `POST_VERIFY_FAIL`
- `EVIDENCE_WRITTEN`
- `EVIDENCE_WRITE_FAILED`

末尾に不完全JSON行がある場合、その行だけを破損行として扱い、それ以前の完結行を失わない。
破損行の存在はSummaryへ記録し、正式ExportはFail Closedとする。

## 5. UPDATED_THIS_RUN
次を全て満たす場合のみ今日の更新成果とする。
- 同一RunIdにExecute対象記録あり
- BeforeAcceptanceDate空欄
- PUT_SUCCEEDEDあり
- POST_VERIFY_PASSあり
- AfterAcceptanceDate = CandidateAcceptanceDate

以前から受入済の案件は`ALREADY_ACCEPTED`であり、今回更新数に含めない。

## 6. 全件Analysis CSV
`App272_AcceptanceAnalysis_ALL_YYYYMMDD_HHmmss.csv`
UTF-8 BOM / RFC4180 / CRLF。

既存AcceptanceSyncの実際の7分類定数を`Class`としてそのまま保存し、
独自分類で置換しない。

別列`EvidenceStatus`:
- UPDATED_THIS_RUN
- ALREADY_ACCEPTED
- CANDIDATE_REMAINING
- REVIEW_REQUIRED
- SOURCE_ONLY
- SOURCE_UNKNOWN

`NO_SOURCE_DATA_UNKNOWN`を「未受入」と断定しない。

### SOURCE_ONLY
SOURCE_ONLYも全件Analysis CSVへ含める。
App272側が存在しないため以下は空欄:
- App272RecordId
- App272Revision
- BeforeAcceptanceDate
- AfterAcceptanceDate
App293側情報とEvidenceStatus=SOURCE_ONLYは保持する。

### 複数受入
`App293RecordCount >= 2`の場合も情報を落とさない。
列名は単数`App293受入番号`ではなく`App293ReceiptNumbers`とする。
全受入番号を正規化・ソートし、`;`区切りで格納する。
ExportVerifyで、列挙した番号数とApp293RecordCountの整合を検証する。
（受入番号重複等で件数定義が異なる場合は、実装時に既存AcceptanceSyncの集約定義を正本とする。）

## 7. 未受入期限超過CSV
`App272_未受入期限超過_YYYYMMDD_HHmmss.csv`

条件:
受入れ日空欄 AND
((納期非空欄 AND 納期 < AsOfDate) OR
 (補助期限非空欄 AND 補助期限 < AsOfDate))

空欄日は超過扱いしない。非空欄不正日付はFail Closed。
当日は超過に含めない。

分類:
- OVERDUE_DUE
- OVERDUE_INSPECTION（補助期限既定=K完成検査日）
- OVERDUE_BOTH
- RECEIPT_EXISTS_ACCEPTANCE_MISSING（外注入荷実績日あり・受入れ日なし）

補助期限は`SecondaryDeadlineFieldCode`/`SecondaryDeadlineLabel`でパラメータ化。
既定はK完成検査日。元依頼の「研修日/検収日」は業務確認なしに固定解釈しない。

## 9. ExportVerify
全件Analysis:
- 元Analysis行数 = CSV行数
- 主要キー/Class一致
- UPDATED_THIS_RUN全件でBefore空欄
- PUT_SUCCEEDED存在
- After=Candidate
- POST_VERIFY_PASS存在
- Execute対象/今回更新件数整合
- SOURCE_ONLYのApp272固有列が空欄
- App293ReceiptNumbersのソート/件数整合
- SHA256成功

期限超過:
- 抽出件数=CSV行数
- 全件受入れ日空欄
- 非空欄期限の少なくとも一方が超過
- 空欄日を超過扱いしていない
- SHA256成功

## 10. Fail Closed
GET/Form Preflight/必須型/既存SafetyStop条件/不正日付/
Analysis行数/実行証跡整合/CSV再読込/SHA256/JSONL破損/
Evidence最終生成の異常はEvidence Export FAIL。
ただし既にPostVerify PASSしたPUT結果を取り消したり再PUTしたりしない。
0件は正常PASS。

## 11. 非変更範囲
以下の既存安全ロジックは変更しない:
- AcceptanceSync 7分類
- Controlled Execute
- MaxWrites=50
- Execute直前再Analysis
- revision付きPUT
- PUT対象=受入れ日のみ
- PostVerify
- No Auto Retry
- MorningRoutine/Phase1C/PhaseB
- 日程編集PUT
- 外注入荷実績日PUT
- ヒートマップ表示

**例外:** AcceptanceSync Execute周辺へ、RunId付きJSONL状態遷移の追記処理を新規追加する。
これは更新判定・PUT条件・PUT内容・revision/PostVerifyを変更するものではない。
ログ書込み失敗を理由に既に成功したPUTを再実行しない。

## 12. 受入テスト
- PUT成功→PostVerify PASS→Evidence書込み失敗:
  PUT成功維持 / `PUT_SUCCESS_EVIDENCE_WRITE_FAILED` / Export FAIL / 再PUTなし
- SOURCE_ONLY: App272固有列空欄、App293情報保持
- 複数受入: ReceiptNumbers全件ソート列挙、RecordCount整合
- JSONL末尾破損: 完結行読取可能、破損検出、Export Fail Closed
- UPDATED_THIS_RUN: Before空欄＋PUT_SUCCEEDED＋PostVerify PASS＋After=Candidate
- 既受入: ALREADY_ACCEPTED、今回更新数0
- App293ソースなし: SOURCE_UNKNOWN、未受入断定禁止
- 納期のみ超過/補助期限のみ超過/両方超過/両方空欄
- 同日再実行: 成果物非上書き
- 全成果物SHA256記録
