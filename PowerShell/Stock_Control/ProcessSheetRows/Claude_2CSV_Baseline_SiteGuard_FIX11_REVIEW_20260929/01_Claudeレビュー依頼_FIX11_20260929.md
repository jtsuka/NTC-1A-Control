## 3. Design requirement being restored
REV5/REV5.1 design defines Baseline metadata as:

```text
K1 = BaselineStatus
L1 = Initialized / NotInitialized
K2 = BaselineInitializedAt
L2 = yyyy/mm/dd hh:mm:ss
K3 = BaselineInitializedSite
L3 = SiteName
```

2CSV normal operation is allowed only when the Baseline belongs to the current SiteName.

FIX10 source still inherited an implementation shortcut:

```text
J1 = BASELINE_INITIALIZED
K1 = timestamp
```

and did not bind the marker to SiteName.

## 4. FIX11 changes to review
### FIX11-01 Formal metadata read
`Get-NewProductHistoryState` reads K1:L3 and returns:
- BaselineMetadataValid
- BaselineInitializedSite
- BaselineExpectedSite
- BaselineSiteMatch
- LegacyMarkerPresent
- BaselineState

`BaselineInitialized=True` only if formal metadata is valid **and SiteName matches**.

### FIX11-02 Fail-closed invalid/mismatched history
For DatasetCount=2:
- legacy J1-only marker -> fail-closed
- valid formal metadata but SiteName mismatch -> fail-closed
- CandidateKey rows exist while formal Baseline metadata is absent -> fail-closed

No automatic repair or source inference.

### FIX11-03 Formal metadata write
`Set-NewProductBaselineInitialized` requires SiteName and writes K1:L3.
String cells use FIX9-proven COM pattern (`NumberFormat="@"` then `[string]Value2`).
Legacy J1 is cleared so rollback to a pre-SiteGuard build does not silently trust a site-less marker.

### FIX11-04 Baseline candidates = 0 edge case
The design explicitly permits initialization with zero Baseline candidates.
If `Set-NewProductBaselineInitialized` itself must create the History sheet, FIX11 also creates A:I headers using the FIX9-safe COM pattern.
This prevents a future Registered row from being written into a metadata-only sheet with no history header.

### FIX11-05 Post-write verification
Immediately after Baseline Initialize:
- reread formal metadata with current SiteName
- require `BaselineInitialized=True`
- otherwise throw before final Save
