| 役割 | 現行(本番) | 現行beta | **新beta** | 内容 |
|---|---|---|---|---|
| Pi GUI | v2.4 | v2.5 beta | **v3.6 beta** | v2.5 beta+ログ+RUN/STOP/MARK |

注意:

- 従来は「GUI v2.N ↔ 通信 v1.3.N」の副番号を揃える規則(v2.4↔v1.3.4、v2.5β↔v1.3.5β)だった。v3.6からは**3本とも同一の番号**に変える。従来規則の延長ではないため、旧版との対応は上の表で追う。
- 3.6は、GUIの系列(v2.4→v2.5β)・通信の系列(v1.3.4→v1.3.5β)のどちらの次の番号でもない。意図的な統一であり、旧番号とは区別される。

- 通信モジュールv3.6βは「内容変更なし」ではなく、**観測フックだけを足した版**である(`set_log_hook()`と各所の`_emit()`呼び出し)。フック未登録なら追加の処理は何も走らない。v1.3.5βとの同一性は試験で確認している(§6)。

## 4. 動作仕様

### 4.1 起動オプション(追加分)

| オプション | 既定 | 内容 |
|---|---|---|
| `--log-dir PATH` | `~/ntc_logs` | ログの保存先 |
| `--no-log` | なし | ログを無効にする(v2.5 betaと同じ動作になる) |

起動は従来どおり明示実行のみ。自動切り替えはしない。

```sh
python3 ntc_pygame_ui_v3_6_beta.py --port /dev/serial0
```

### 4.2 画面の追加(既存の配置は変更なし)

- 上段の右側(ポート選択とEXITの間)に、`LOG 1234`(緑)、`LOG ERR`(赤)、`LOG OFF`(灰)の表示。
- 設定欄とログ行の間の空き帯に、小さなボタン3つ。`RUN` `STOP` `MARK`。押すとログに時刻付きの`NOTE`行が入る。制御には一切影響しない。
- 1024×600と800×480の画面で、既存の部品との重なりがないことを座標計算で確認した(実画面での目視は未実施)。

### 4.3 CSVの形式

列: `wall_time, mono_s, event, hex, wind_length, actual_tension, rx_status, detail`

| event | 内容 |
|---|---|
| `START` | ファイルごとに1行。GUI/通信/ログの版、ポート、ホスト名、Python版 |
| `RX_RAW` | 1回のserial readで得たバイト列(フレーム分解前) |
| `RX_FRAME` | 正常なDirection-Bフレーム。hex、WIND LENGTH、テンション値(列名は`actual_tension`、画面では`TENS ADC`)、前フレームからの間隔`dt=…ms` |
| `RX_BOOT` | ESP32のBoot Magic |
| `RX_LEGACY` | 従来のチェックサム付き12/8バイト |
| `RX_DROP` | 再同期のために捨てた1バイト(ノイズや同期ずれの指標) |
| `RX_ERR` | serial read例外 |
| `TX` / `TX_ERR` | Piが送ったコマンドのバイト列とラベル |
| `STATUS` | RX STATUSの遷移(WAIT/OK/LOST)と直前の状態 |
| `NOTE` | RUN / STOP / MARK |
| `PORT` | ポートの開閉 |
| `SUMMARY` | 60秒ごとの累計カウンタと、区間内の`dt`最小・最大 |
| `STOP` | ログ終了と最終カウンタ |

### 4.4 安全設計

- 受信スレッドは、キューに入れるだけ(`put_nowait`)。ファイル書き込みは別スレッド。書き込みが遅れても受信を取りこぼさない。
- キュー(2万件)があふれたら、そのイベントを捨ててカウントする。受信を待たせない。
- ログ側で例外が出ても、通信側ではすべて握りつぶす。ログ失敗でGUIも受信も止まらない。
- 生バイトは解析の前に記録する。パーサに不具合があっても証拠は失われない。
- 保存先を作れない/書けない/ディスク残量が200 MB未満の場合は、ログだけを止め、`LOG ERR`を表示する。GUIは動き続ける。
- 1ファイル10 MBで分割(`rxlog_日時_partNN.csv`)。合計500 MBを超えたら、**このモジュールが作った`rxlog_`ファイルのうち古いものだけ**を削除する。他のファイルには触れない。
- 書き出しは2秒ごと、`fsync`は30秒ごと。電源断で失うのは直近数十秒まで。
- 容量の見込み: 約1.5 MB/時間(約3フレーム/秒の場合、模擬試験の実測から算出)。

## 5. 未決事項と既知の限界

- **反映済み**: GUIのテンション表示名を `ACTUAL TENSION` から **`TENS ADC`** に変更した(ラベル文字のみ。内部のキー名と処理は不変)。根拠はTC106原典(`History/FW_TC106-1_v0.0_250201.c`): `tens_actual`はAN0(RA0)を16回読んだADC値の平均(`tens_sum >> 4`)で、送信値も`tens_actual`そのもの(零点`tens_zero`を引いた`tens_temp`ではない)。ADCは`AD1CON1=0x00E0`(AD12B=0)から10ビットと読め、値は0〜1023(DERIVED)。つまり**零点補正前のセンサー入力のカウント値**であり、電圧でも張力(gf)でもない。校正関係は未確認のため、画面にgf等の単位は付けない。
- 旧ラベルより短いので、右列のラベルと値の枠は重なりにくくなる(実画面での目視は未実施)。
- **UNRESOLVED**: 実機Pi(7インチ画面)での目視確認は未実施。ボタン位置は座標計算のみで確認した。
- Piには時計(RTC)がない場合がある。`wall_time`が狂っていても、`mono_s`(起動からの経過秒)で相対時刻は正しい。
- `dt`はPiがESPから受け取った時刻の間隔である。TC106→ESPの実際の周期(約0.34秒、DERIVED)の確定には、ロジアナによる確認が引き続き必要。
- `TX`行はPiからESPへ送ったことの記録であり、TC106に届いたことの証拠ではない。
- ログには、どのTC106(各CHグループ内の共有バス)のデータかを識別する情報はない(識別方式は未解明)。
- 現地では通信環境がない場合がある。ログの回収は、USBメモリ経由を想定する。

確認した内容:

- 同じ入力(ノイズ13バイト、Boot Magic、正常フレーム、チェックサム付きフレーム、分割到着)を v1.3.5β と v3.6β に与え、**出力メッセージ・受信値が完全に一致**する。
- 送信バイト列(SENS.ADJ / 張力 / RESET)が v1.3.5β と同一。
- フックが受け取るイベントの種類・値(`17 05 01 07 03 7F` → 10523 / 37、`00 00 00 03 66 7F` → 0 / 1023)。ノイズ13バイトは13件の`rx_drop`として全数記録される。
- フックが例外を投げても、受信と送信が正常に続く。
- ログのCSV内容、状態遷移、SUMMARY、分割、古いファイルの削除(他のファイルが残ること)、キューあふれ時に待たされないこと、ディスク残量不足、書き込み不可のフォルダ。
- GUI v3.6βのソース契約: 新しい版をimportすること、既存の操作関数(`on_pad`など)がv2.5βとAST上で同一であること、ログの登録がポートを開く前であること、終了時に停止すること。
- 模擬受信3000フレームで、ログの取りこぼしなし(あふれ0)。1フレームあたり約139バイトのCSV。

**実機でのPASSは主張しない。** 以下の手順で確認する。
